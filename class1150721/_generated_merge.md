### 核心概念說明

#### 1. 大語言模型（Large Language Model，LLM）

大語言模型是一種以海量文字資料訓練而成的 AI 系統，能夠理解並生成自然語言。

**一個簡單的比喻：**
想像有一位助理，他從小閱讀了幾乎所有的書籍、文章、程式文件與對話紀錄。當你給他一個問題或指令，他會根據所有學過的知識生成一個最合理的回應。這就是 LLM 的運作方式。

**常見的 LLM 產品：**

目前全球 LLM 產業呈現「美中並進」的態勢，美國廠商在通用能力與生態系整合上持續領先，中國廠商則以開源、高性價比與快速迭代急起直追。

*美國廠商：*

| 產品 | 開發商 | 特點 |
|------|--------|------|
| GPT-5.6 | OpenAI | 目前最新旗艦模型，業界最主流、生態系與工具鏈完整 |
| Claude Opus 4.8 | Anthropic | 目前最新旗艦模型，強調安全性、長文本與 Agent 代理型工作流 |
| Gemini 3.5 Pro | Google | 目前最新旗艦模型，支援多模態推理與超長上下文 |

*中國廠商：*

| 產品 | 開發商 | 特點 |
|------|--------|------|
| DeepSeek V4 | DeepSeek（深度求索） | 推理能力強、成本極低，開源生態活躍 |
| Qwen3-Max | 阿里巴巴 | 通義千問系列最新旗艦，全模態（文字／圖片／音訊／影片） |
| GLM-5 | 智譜 AI | 工具調用能力強，重視 Agent 場景應用 |
| Kimi K2 | Moonshot AI（月之暗面） | 強化多 Agent 協作與長任務處理能力 |
| MiniMax M2 | MiniMax（稀宇科技） | 支援百萬級上下文與原生多模態 |

> 提醒：以上為 2026 年年中的代表性旗艦模型，AI 產業版本迭代極快，實際最新版本請以各廠商官網公告為準；教學重點在理解「不同產品的定位差異」，而非記憶特定版本號。

**LLM 的核心能力：**

- **文字生成（Text Generation）**：根據輸入的 Prompt 產出文字內容
- **語意理解（Semantic Understanding）**：理解語境與隱含意圖，不只是字面意思
- **指令遵循（Instruction Following）**：根據具體指令執行特定任務
- **推理與分析（Reasoning）**：進行多步驟的邏輯推論

**LLM 在產業的實際應用：**

- 客服自動回覆：全天候回應客戶常見問題
- 文件摘要與分析：快速萃取大量報告的關鍵資訊
- 程式碼自動生成：加快軟體開發速度
- 行銷文案量產：針對不同受眾快速生成內容
- 資料分類與標記：自動整理非結構化資料

#### 2. AI Agent 系統架構

AI Agent（AI 代理）是一種能夠**自主執行複雜任務**的 AI 系統。與普通的 LLM 對話不同，Agent 具有完整的「感知 → 思考 → 規劃 → 行動」迴圈。

**直覺的比喻：**

想像你雇用了一位助理，你告訴他：「幫我調查三個競爭對手的定價，整理成 Excel 報表後寄給我。」

- 助理會**自行規劃步驟**：搜尋網路 → 瀏覽各官網 → 紀錄資料 → 開啟 Excel → 填寫資料 → 寄送郵件
- 全程不需要你一步一步指示，他會自己完成

AI Agent 就是能夠**自主規劃並執行多步驟任務**的 AI 系統。

**Agent 的四大組成要素：**

```
          使用者任務指令
                │
                ▼
    ┌─────────────────────┐
    │                     │
    │   大腦（LLM）        │   ← 理解任務、制定決策
    │                     │
    └──────────┬──────────┘
               │
               ▼
    ┌─────────────────────┐
    │                     │
    │  規劃器（Planner）   │   ← 將複雜任務拆解為可執行步驟
    │                     │
    └──────────┬──────────┘
               │
               ▼
    ┌─────────────────────┐
    │                     │
    │   工具集（Tools）    │   ← 瀏覽器、程式執行器、API、檔案讀寫...
    │                     │
    └──────────┬──────────┘
               │
               ▼
    ┌─────────────────────┐
    │                     │
    │   記憶體（Memory）   │   ← 儲存過去的對話與執行紀錄
    │                     │
    └─────────────────────┘
```

#### 3. Vibe Coding

**Vibe Coding** 是一種以**自然語言驅動**程式碼生成的開發方式。你不需要自己寫每一行程式語法，只需要用白話文描述你想要做的事，由 AI 工具（如 GitHub Copilot）幫你生成可執行的程式碼。

**Vibe Coding 的長處：**

- 大幅降低程式設計的學習門檻
- 快速將想法轉化為可執行的自動化工具
- 讓非技術背景的業務人員也能構建流程
- 加快原型（Prototype）開發速度

**Vibe Coding 的限制：**

- AI 生成的程式碼可能包含錯誤，**必須人工驗證**
- 對非常複雜或高安全需求的系統有一定侷限
- 若描述需求不清楚，AI 可能生成不符合期望的程式碼
- 不適合直接用於需要高精確度的核心系統

**傳統開發 vs. Vibe Coding 比較：**

| | 傳統開發 | Vibe Coding |
|--|---------|-------------|
| 前置要求 | 熟悉程式語法與演算法 | 能清楚描述需求 |
| 開發速度 | 依工程師熟練度而定 | 快速產出原型 |
| 結果可靠性 | 工程師掌控 | 需人工驗證 |
| 適合場景 | 核心系統、高安全性 | 自動化工具、快速驗證 |

#### 4. OpenClaw 平台簡介

**OpenClaw** 是目前產業廣泛採用的 AI Agent 視覺化開發平台，讓使用者以**拖拉積木**的方式組合 AI 工作流程，大幅降低 Agent 系統的開發難度。

**OpenClaw 的主要特色：**

- 直覺的視覺化流程編輯介面
- 支援串接多種 LLM 後端（GPT、Claude、Llama 等）
- 內建豐富的工具節點：網頁搜尋、讀取檔案、呼叫 API、資料庫操作等
- 支援多個 Agent 相互協作完成複雜任務

本課程後續堂次將會實際使用 OpenClaw 構建各種自動化 Agent 系統。

#### 5. LLM 與 Agent 的資安風險

在學習 AI Agent 開發的同時，我們也必須了解其潛在的資安風險，才能在設計系統時做出正確的防護措施。

**主要風險類型：**

| 風險類型 | 說明 | 防護方向 |
|---------|------|---------|
| **Prompt Injection** | 惡意使用者透過精心設計的輸入，操控 AI 執行非預期的行為 | 對外部輸入進行驗證與過濾 |
| **資料洩漏** | Agent 在執行任務時可能不慎將敏感資料傳送至外部 LLM | 避免將機密資料送入外部 API |
| **過度授權** | Agent 被賦予超出任務所需的系統權限 | 遵循「最小權限原則」 |
| **幻覺（Hallucination）** | LLM 生成看似合理但實際錯誤的資訊 | 重要輸出需人工核實 |

> **重要觀念：** LLM 因為訓練方式的特性，有時會「自信地給出錯誤答案」。這在 Agent 系統中尤其危險，因為錯誤的決策會直接驅動工具執行行動。設計 Agent 時，務必在關鍵決策點加入人工確認機制。

### 程式碼範例（虛擬碼）

#### 基礎 LLM 對話程式

```
# === 初始化 ===
載入 openai 套件
設定 API_KEY = 從環境變數讀取("OPENAI_API_KEY")

# === 初始化對話歷史 ===
對話歷史 = []

# === 主要對話迴圈 ===
重複執行:
    讀取 使用者輸入

    如果 使用者輸入 == "exit":
        顯示 "再見！"
        結束程式

    將「使用者訊息」加入對話歷史

    呼叫 LLM API:
        傳入: [模型名稱, 對話歷史]
        接收: AI 回應文字

    將「AI 回應」加入對話歷史
    顯示 AI 回應
```

#### 加入工具調用的基礎 Agent 機制

```
# === 定義可用工具 ===
工具A: 讀取檔案(檔案路徑) → 回傳檔案內文字
工具B: 寫入檔案(檔案路徑, 文字內容) → 儲存到檔案
工具清單 = [工具A, 工具B]

# === Agent 決策迴圈 ===
函式 Agent執行(任務描述):
    重複執行 直到任務完成:

        給 LLM 的輸入 = {
            系統指令: "你是一個能操作檔案的 AI 助理",
            任務: 任務描述,
            可用工具: 工具清單的名稱與說明,
            過去執行結果: 執行歷史
        }

        LLM 決策 = 呼叫 LLM(給 LLM 的輸入)

        如果 LLM 決定使用某個工具:
            執行該工具，取得結果
            將結果記錄到執行歷史
        否則（LLM 認為任務完成）:
            回傳最終答案
```

---

### 核心概念說明

#### 1. 自動化引擎的核心架構

一個自動化流程（不論是人工執行的 SOP，還是 AI Agent），都可以拆解為三個核心元素：

```
輸入（Input）
    │
    ▼
決策邏輯（Decision Logic）
  ├── 如果 A → 執行 X
  ├── 如果 B → 執行 Y
  └── 如果 C → 重複嘗試
    │
    ▼
輸出（Output）
```

對 AI Agent 而言，**決策邏輯**是由 LLM 動態生成的，而不是人工寫死的規則。

**AI Agent 自動化流程的完整運作週期：**

| 階段 | 說明 | 對應程式概念 |
|------|------|------------|
| 接收任務 | 使用者或系統給出指令 | 函式的輸入參數 |
| 拆解步驟 | LLM 規劃執行計畫 | 演算法設計 |
| 執行行動 | 呼叫工具完成子任務 | 函式呼叫 |
| 確認結果 | 判斷子任務是否成功 | 條件判斷 |
| 錯誤處理 | 若失敗則嘗試替代方案 | 例外處理 |
| 回報完成 | 輸出最終結果 | 回傳值 |

---

#### 2. 控制流：條件判斷（Condition）

**條件判斷**是自動化流程中最基本的決策機制：「如果滿足某個條件，就做 A；否則就做 B。」

**實際情境範例：**

你要設計一個自動回覆郵件的 Agent：
- **如果** 郵件主旨包含「請款」→ 轉交財務處理
- **如果** 郵件主旨包含「抱怨」→ 轉交客服主管
- **否則** → 自動生成標準回覆

**條件判斷的虛擬碼結構：**

```
如果 條件A 為真:
    執行動作A
否則如果 條件B 為真:
    執行動作B
否則:
    執行預設動作
```

**在 Agent 中的應用：**

```
如果 LLM 的決策 == "呼叫工具":
    執行指定工具
否則如果 LLM 的決策 == "任務完成":
    回傳最終結果
否則如果 LLM 的決策 == "需要更多資訊":
    詢問使用者補充資訊
```

---

#### 3. 控制流：迴圈（Loop）

**迴圈**讓程式能夠**重複執行**某段邏輯，直到滿足特定條件為止。這在 Agent 中非常關鍵——Agent 必須持續「思考 → 行動 → 觀察結果 → 再思考」，直到任務完成。

**兩種常見的迴圈類型：**

| 類型 | 說明 | 應用場景 |
|------|------|---------|
| **計數迴圈** | 執行固定次數後停止 | 批次處理 100 筆資料 |
| **條件迴圈** | 滿足條件才停止 | Agent 持續執行直到任務完成 |

**Agent 執行迴圈（條件迴圈）：**

```
重複執行 直到 任務完成:
    思考當前狀態
    決定下一個行動
    執行行動
    觀察結果
    更新對任務的理解
```

**批次處理迴圈（計數迴圈）：**

```
對 每一筆資料 在 資料清單 中:
    處理這筆資料
    儲存處理結果
```

> **注意：** 條件迴圈需要確保**終止條件**一定能被達到，否則程式會陷入「無限迴圈」，永遠無法停止。Agent 設計中通常會設定「最大嘗試次數」作為安全機制。

---

#### 4. 錯誤處理與容錯補償機制

自動化系統在執行過程中，**錯誤幾乎是必然發生的**：網路連線中斷、API 回應逾時、資料格式不符……等等。

好的自動化系統必須能夠：
1. **偵測錯誤**：知道哪裡出了問題
2. **分類錯誤**：是可以重試的暫時性錯誤，還是必須停止的嚴重錯誤？
3. **補償行動**：執行替代方案或通知人工介入

**常見的容錯策略：**

| 策略 | 說明 | 適用情境 |
|------|------|---------|
| **重試（Retry）** | 自動重新嘗試，最多 N 次 | API 暫時逾時、網路不穩定 |
| **等待後重試（Exponential Backoff）** | 每次重試間隔越來越長 | API 呼叫頻率限制 |
| **替代方案（Fallback）** | 主要方案失敗時，使用備用方案 | 主要 LLM 故障時換用備用模型 |
| **人工介入通知** | 發送警告，請人工處理 | 無法自動修復的嚴重錯誤 |

---

#### 5. 工具調用（Tool Use）：讓 Agent 能「做事」

單純的 LLM 只能「說話」，而 Agent 的強大之處在於能夠「做事」——這是透過**工具調用（Tool Use）**實現的。

**工具的概念：**

工具是一個有明確輸入與輸出的函式。Agent（LLM）在決策時，會選擇呼叫哪個工具、傳入什麼參數，然後根據工具的回傳結果決定下一步。

**常見工具類型：**

| 工具類型 | 功能 | 範例 |
|---------|------|------|
| 搜尋工具 | 搜尋網路或資料庫 | Google Search API |
| 檔案工具 | 讀取/寫入本機檔案 | 讀取 CSV、寫入 TXT |
| 計算工具 | 執行數學運算 | Python 計算機 |
| 通訊工具 | 發送郵件、訊息 | Outlook、Line API |
| 瀏覽器工具 | 操控網頁 | Playwright、Selenium |

**工具調用的完整流程：**

```
使用者任務 → LLM 分析任務
  │
  ├─ LLM 說「我需要使用搜尋工具，關鍵字為 XXX」
  │       │
  │       ▼
  │   程式執行搜尋工具(關鍵字="XXX")
  │       │
  │       ▼
  │   取得搜尋結果，傳回給 LLM
  │
  ├─ LLM 說「我需要寫入檔案，內容為 YYY」
  │       │
  │       ▼
  │   程式執行寫入檔案工具(內容="YYY")
  │
  └─ LLM 說「任務完成」→ 回傳最終答案
```

最大重試次數 = 3
對話歷史 = [

            顯示 "發生未知錯誤，停止重試"
            拋出例外

    顯示 "已達最大重試次數，請檢查網路連線"
    結束程式

# === 主對話迴圈 ===
重複執行:
    使用者輸入 = 從終端機讀取()

    如果 使用者輸入 == "exit":
        結束程式

    將使用者輸入加入對話歷史
    AI 回應 = 呼叫LLM(對話歷史)
    將 AI 回應加入對話歷史
    顯示 AI 回應
```

```

        內容 = 開啟並讀取(檔案路徑)
        回傳 內容

    嘗試:
        開啟檔案(檔案路徑) 並寫入 文字內容
        回傳 "成功寫入檔案"

    對話歷史 = [系統提示 + 工具說明 + 使用者指令]

    重複執行 最多 10 次:
        LLM回應 = 呼叫LLM(對話歷史)

        如果 LLM回應.類型 == "呼叫工具":
            工具名 = LLM回應.工具名稱
            參數  = LLM回應.工具參數
            工具結果 = 工具清單[工具名](參數)
            將工具結果加入對話歷史

        否則如果 LLM回應.類型 == "最終回答":
            回傳 LLM回應.內容

    回傳 "已達最大步驟數，任務未完成"
```

## 8/04｜第03堂｜巨量數據調度工程與非結構化資料轉換

### 學習目標

完成本堂課後，學員將能夠：

- 說明 AI Agent 處理大量資料的典型架構與流程
- 區別「結構化資料」與「非結構化資料」的差異
- 使用程式對試算表（Excel / CSV）進行讀取、篩選、排序與寫入
- 建立批次處理流程，自動化彙整來自多份活頁簿的異質資料

---

### 核心概念說明

#### 1. 為什麼資料處理是 Agent 的核心能力？

在企業環境中，大量的工作時間花費在「整理資料」上：

- 把多份 Excel 報表合併成一份
- 從上百筆記錄中找出符合條件的資料
- 將不同格式的資料統一成標準格式

這些工作**重複性高、規則性強**，是 AI Agent 最能發揮價值的場景。

**一個典型的企業痛點：**

> 每個月月底，業務助理要花一整天，手動把 20 個業務員各自回傳的 Excel 報價單，複製貼上到一份匯總表裡，然後再計算每個業務的總業績。

如果用 Agent 處理，整個流程可以在幾分鐘內完成。

---

#### 2. 結構化資料 vs. 非結構化資料

| | 結構化資料 | 非結構化資料 |
|-|-----------|-------------|
| **定義** | 有固定格式，可直接用程式讀取 | 沒有固定格式，需要解析才能使用 |
| **範例** | Excel 表格、CSV 檔、資料庫 | PDF 報告、電子郵件、掃描圖片 |
| **處理難度** | 相對容易 | 需借助 AI 或 OCR 技術 |
| **典型工作** | 篩選、排序、計算 | 資訊提取、摘要、分類 |

**從非結構化轉為結構化的典型流程：**

```
原始資料（PDF 合約、郵件內文、掃描文件）
    │
    ▼ AI / OCR 解析
提取關鍵欄位（廠商名稱、金額、日期）
    │
    ▼ 資料清理與驗證
結構化資料表（可存入 Excel 或資料庫）
    │
    ▼ 後續分析與報表生成
最終報告
```

---

#### 3. Excel / CSV 自動化處理

在 Python 中，處理試算表最常用的工具是：

| 工具 | 適用情境 | 特點 |
|------|---------|------|
| **openpyxl** | 讀寫 `.xlsx` 格式的 Excel | 可保留原有格式、樣式 |
| **pandas** | 大量資料的分析與計算 | 功能強大，適合數據分析 |
| **csv 模組** | 讀寫 `.csv` 純文字表格 | 輕量，適合簡單場景 |

**試算表操作的基本動作：**

| 動作 | 說明 |
|------|------|
| 讀取（Read） | 從檔案載入資料到程式 |
| 篩選（Filter） | 只取出符合條件的列 |
| 排序（Sort） | 依照某欄位大小排列順序 |
| 計算（Calculate） | 加總、平均、計數等 |
| 寫入（Write） | 把處理結果存回檔案 |

---

#### 4. 跨活頁簿資料整合（批次處理）

**批次處理（Batch Processing）**是指一次性處理大量同類型任務，而不是一筆一筆手動處理。

**跨活頁簿整合的典型場景：**

```
資料夾結構：
  /業務報表/
    ├── 北區業務_王大明.xlsx
    ├── 中區業務_李小華.xlsx
    ├── 南區業務_張美玲.xlsx
    └── ... (共 20 個檔案)

目標：
  自動讀取所有檔案 → 彙整到一份 匯總表.xlsx → 計算各業務業績合計
```

**批次處理的核心邏輯：**

```
步驟1：找到所有需要處理的檔案
列出資料夾內所有 .xlsx 檔案 → 得到一個檔案清單

步驟2：逐一處理每份檔案（迴圈）
對 每個檔案 在 檔案清單 中:
    讀取該檔案的資料
    提取需要的欄位
    將資料加入「總彙整清單」

步驟3：整理與計算
對 總彙整清單 進行排序、計算、格式化

步驟4：輸出結果
將整理後的資料寫入新的 Excel 檔案
```

---

#### 5. AI 在資料處理中的角色

傳統的資料處理需要明確的規則（「如果欄位 A 等於 X，就…」）。但現實世界的資料往往**格式不統一**，這時 AI 就能發揮作用：

**AI 的三個關鍵角色：**

| 角色 | 說明 | 範例 |
|------|------|------|
| **格式識別** | 理解不同格式的資料代表什麼 | 「NT$12,000」「12000元」都代表 12000 元 |
| **缺失值補充** | 根據上下文推斷缺失的資訊 | 從「台北辦公室」推斷地區為「北區」 |
| **異常偵測** | 找出資料中不合理的值 | 業績填寫為負數 → 可能是錯誤 |

### 核心概念說明

#### 1. 為什麼需要 Web 自動化？

許多企業的重要資料仍然存放在各種網路平台上，例如：

- 政府開放資料平台
- 電商平台上的競品價格
- 產業研究報告網站
- 公司內部的 ERP / CRM 系統

這些資料通常**無法透過 API 直接取得**，只能透過「模擬人類操作瀏覽器」的方式來擷取。

---

#### 2. Web 爬蟲 vs. Web 自動化

這兩個概念常被混用，但技術上有明確的差異：

| | Web 爬蟲（Scraping） | Web 自動化（Automation） |
|-|---------------------|------------------------|
| **核心目的** | 大量擷取網頁上的文字資料 | 模擬使用者在瀏覽器的操作行為 |
| **主要技術** | requests + BeautifulSoup | Playwright、Selenium |
| **能做什麼** | 讀取靜態網頁內容 | 點擊按鈕、填表、登入、處理動態頁面 |
| **適用情境** | 新聞抓取、靜態資料庫 | 需要登入的系統、動態載入的內容 |
| **限制** | 無法處理 JavaScript 動態內容 | 速度較慢，資源消耗較多 |

---

#### 3. 瀏覽器自動化技術：Playwright

**Playwright** 是由 Microsoft 開發的現代瀏覽器自動化框架，能夠控制 Chrome、Firefox、Safari 等瀏覽器，執行各種使用者操作。

**Playwright 能做到的事：**

| 操作 | 說明 |
|------|------|
| 開啟網頁 | 導航至任意 URL |
| 點擊元素 | 點擊按鈕、連結、核取方塊 |
| 填寫表單 | 輸入文字、選擇下拉選單 |
| 擷取資料 | 取得網頁上的文字、圖片、連結 |
| 截圖 | 對目前頁面截圖 |
| 等待元素 | 等到特定內容出現才繼續 |
| 處理彈出視窗 | 確認對話方塊、切換分頁 |
| 下載檔案 | 觸發下載並儲存到本機 |

**認證流程自動化（重要概念）：**

很多平台需要先登入才能存取資料。自動化登入的基本流程：

```
1. 開啟登入頁面
2. 找到「帳號」輸入框，填入帳號
3. 找到「密碼」輸入框，填入密碼
4. 點擊「登入」按鈕
5. 等待頁面跳轉完成
6. 確認登入成功（尋找登入後才有的元素）
7. 繼續執行後續任務
```

> **資安提醒：** 帳號密碼務必從環境變數讀取，絕對不能寫死在程式碼中，更不能上傳到 GitHub。

---

#### 4. 網路反爬蟲機制與道德規範

**技術面的挑戰：**

許多網站會設置防護機制來阻擋自動化程式：

| 防護機制 | 說明 |
|---------|------|
| CAPTCHA | 要求驗證使用者是人類 |
| 速率限制 | 太頻繁的請求會被封鎖 |
| User-Agent 檢查 | 識別並封鎖非瀏覽器的請求 |
| IP 封鎖 | 短時間大量請求會被封鎖 IP |

**道德與法律規範：**

- 使用前請閱讀網站的**服務條款（Terms of Service）**，確認是否允許自動化存取
- 避免對目標網站造成不必要的伺服器負載（請求間隔應適當）
- 不應用於爬取受版權保護的內容或個人隱私資料
- 若網站提供 API，應優先使用 API 而非爬蟲

#### 5. Docker 基礎概念

**Docker** 是一種「容器化」技術，可以把程式及其所有相依套件**打包在一個獨立、可攜帶的容器**中，確保在任何電腦上都能以完全相同的方式執行。

**一個簡單的比喻：**

想像 Docker 容器就像是一個**預先配置好環境的虛擬電腦**：
- 所有需要的軟體都已預先安裝
- 不會受到你電腦現有環境的干擾
- 在任何機器上執行結果都一樣

**Docker 的核心概念：**

| 概念 | 說明 | 生活比喻 |
|------|------|---------|
| **Image（映像檔）** | 包含程式與環境的模板 | 食譜 |
| **Container（容器）** | 根據 Image 運行的實際程序 | 依照食譜做出來的料理 |
| **Registry** | 存放 Image 的倉庫 | 食譜書 |
| **Volume** | 容器與主機間的資料共享 | 共用材料箱 |

**常用 Docker 指令（示意）：**

```
# 下載 Image
docker pull [image名稱]

# 啟動容器
docker run [選項] [image名稱]

# 查看執行中的容器
docker ps

# 停止容器
docker stop [容器ID]
```

## 8/18｜第05堂｜智慧通訊協作：電子郵件與 Office 流程自動化

### 學習目標

完成本堂課後，學員將能夠：

- 使用 AI 對郵件進行語意分析，識別意圖與優先順序
- 自動化下載與解析郵件附件
- 根據郵件內容觸發對應的回覆邏輯與任務分派
- 整合郵件與行事曆，實現會議排程自動化

---

### 核心概念說明

#### 1. 為什麼郵件自動化是企業的重要場景？

電子郵件是企業最主要的通訊工具之一，但也是效率瓶頸的來源：

- 平均每位知識工作者每天花費 **2.5 小時**處理電子郵件
- 大量郵件是重複性的：確認收到、請款、詢問狀態
- 重要郵件容易淹沒在垃圾訊息中，造成遺漏

AI Agent 能夠 24 小時不間斷地監控、分類、回覆並分派郵件任務。

---

#### 2. Outlook 自動化的技術選項

在 Windows 環境下，操控 Outlook 主要有以下幾種方式：

| 技術 | 說明 | 適合情境 |
|------|------|---------|
| **win32com（pywin32）** | 透過 Windows COM 介面控制 Outlook 應用程式 | 本地 Outlook 桌面版 |
| **Microsoft Graph API** | 透過 Microsoft 官方 API 存取郵件、行事曆 | 雲端 M365 環境 |
| **exchangelib** | Python 套件，連接 Exchange Server | 企業 Exchange 環境 |
| **IMAP / SMTP** | 標準郵件協定，跨平台 | 非 Outlook 的郵件服務 |

本堂課主要以 **win32com** 示範本地 Outlook 操作，以及介紹 **Microsoft Graph API** 的概念作為現代化替代方案。

---

#### 3. 郵件的語意分析

**語意分析（Semantic Analysis）**是指理解文字背後的**真實意圖**，而不只是字面上的詞彙。

**傳統規則方式 vs. AI 語意分析：**

| | 傳統關鍵字規則 | AI 語意分析 |
|-|--------------|-----------|
| 識別「催款」郵件 | 只能識別包含「請款」「付款」等關鍵字 | 能理解「我們上個月的發票還沒收到款項」也是催款意圖 |
| 識別「投訴」郵件 | 只能識別「抱怨」「不滿」等詞 | 能識別語氣委婉但明確表達不滿的郵件 |
| 多語言支援 | 需要為每種語言維護不同的規則 | 同樣的 Prompt 即可處理中、英、日文郵件 |

**郵件語意分析的典型分類任務：**

| 分析維度 | 可能的分類結果 |
|---------|--------------|
| 意圖分類 | 詢問報價、確認訂單、申請退款、投訴、一般諮詢 |
| 優先級判斷 | 緊急、一般、低優先 |
| 情感分析 | 正面、中性、負面 |
| 需要回覆？ | 是、否 |
| 對應部門 | 業務、財務、客服、技術支援 |

---

#### 4. 附件處理自動化

郵件附件是企業資訊交換的重要媒介，常見的附件處理需求：

- **PDF**：合約、發票、報告 → 提取文字內容
- **Excel**：資料報表 → 讀取並彙整資料
- **Word**：文件草稿 → 提取內容進行摘要
- **圖片**：掃描文件 → OCR 文字識別

**附件自動化處理流程：**

```
收到郵件
    │
    ├── 是否有附件？
    │       │ 是
    │       ▼
    │   判斷附件類型
    │       ├── PDF → 使用 PDF 解析工具提取文字
    │       ├── Excel → 使用 pandas 讀取資料
    │       └── 圖片 → 使用 OCR 或 AI Vision 識別
    │       │
    │       ▼
    │   將提取內容傳給 LLM 進行分析
    │       │
    │       ▼
    │   根據分析結果觸發對應動作
    │
    └── 無附件 → 直接進行郵件內文分析
```

---

#### 5. 行事曆同步自動化

**常見的會議排程自動化場景：**

- 客戶寄來「請問下週可以開會嗎？」→ AI 查看行事曆空檔，自動回覆可用時間
- 收到會議邀請郵件 → 自動建立行事曆事件並設定提醒
- 定期報告完成 → 自動安排下次討論會議

**行事曆操作的基本元素：**

| 元素 | 說明 |
|------|------|
| 事件標題 | 會議名稱 |
| 開始/結束時間 | 日期與時段 |
| 地點 | 實體地點或線上連結 |
| 與會者 | 邀請對象的 Email |
| 提醒 | 會議前多少分鐘提醒 |
| 重複設定 | 每週固定時段的例行會議 |

### 學習目標

---

### 核心概念說明

#### 1. 為什麼「檔案管理與傳統系統整合」是實務中的重要需求？

在實際的企業環境中，有大量未被數位化或 API 化的工作：

**常見的企業痛點：**

| 情境 | 問題 |
|------|------|
| 每月收到數百份 PDF 發票 | 需要手動打開每份、複製金額和日期到 Excel |
| 公司使用 20 年前的進銷存系統 | 系統無法匯出資料，只能靠人工抄寫 |
| 員工桌面資料夾一片混亂 | 找不到資料，版本管理混亂 |
| 掃描文件需要數位化 | 大量紙本資料未被有效利用 |

這些場景沒有可用的 API，只能透過「模擬人類操作」的方式自動化。

---

#### 2. 檔案系統操作

Python 提供了豐富的標準函式庫來處理檔案和資料夾：

| 模組 | 主要用途 |
|------|---------|
| `os` | 基礎的作業系統操作（路徑、目錄、環境變數） |
| `pathlib` | 現代化的路徑處理（推薦使用） |
| `shutil` | 檔案複製、搬移、刪除、壓縮 |
| `glob` | 依照模式搜尋檔案（支援萬用字元） |
| `watchdog` | 監控資料夾，偵測新檔案的出現 |

**常見的檔案自動化任務：**

```
資料夾整理：
    掃描指定資料夾
    依照副檔名分類（.pdf → PDF資料夾、.xlsx → Excel資料夾）
    依照日期分類（今年/去年、月份）
    依照檔案命名規則分類

批次重新命名：
    讀取所有符合條件的檔案
    依照規則生成新的檔名（例如：加上日期前綴）
    重新命名並記錄對照表

自動備份：
    監控重要資料夾的異動
    偵測到新增或修改時，自動複製到備份位置
    保留指定數量的歷史版本
```

---

#### 3. PDF 非結構化資料提取

PDF 是企業中最常見的文件格式，但它的資料不像 Excel 那樣容易讀取。

**PDF 的兩種主要類型：**

| 類型 | 說明 | 提取方式 |
|------|------|---------|
| **文字型 PDF** | 由電腦直接生成，文字可被搜尋 | pdfplumber、pdfminer |
| **掃描型 PDF** | 紙本文件掃描成 PDF，本質上是圖片 | OCR（光學字元識別）工具 |

**常見的 PDF 提取工具：**

| 工具 | 特色 |
|------|------|
| **pdfplumber** | 精確提取文字與表格結構，適合文字型 PDF |
| **PyMuPDF（fitz）** | 速度快、功能多，適合大批量處理 |
| **Tesseract + pytesseract** | 開源 OCR 引擎，適合掃描型 PDF |
| **Azure AI Document Intelligence** | 雲端 AI，準確率高，適合複雜版面 |

**AI 輔助的 PDF 資料提取流程：**

```

    "稅額": 2500,
    "總計": 55000

    │
    ▼ 寫入 Excel 或資料庫
結構化資料
```

#### 4. 桌面 UI 自動化（RPA 概念）

**RPA（Robotic Process Automation，機器人流程自動化）**是一種讓電腦程式模擬「人類操作滑鼠和鍵盤」的技術，讓傳統桌面軟體也能被自動化控制。

**為什麼需要 RPA？**

許多企業有使用了 10-20 年的系統：
- 老舊 ERP 系統（進銷存、財會）
- 政府平台（需要手動填寫大量欄位）
- 不提供 API 的第三方軟體

這些系統唯一的操作方式就是「人坐在電腦前點選」，RPA 讓機器人來做這件事。

**Python UI 自動化工具：**

| 工具 | 適用場景 |
|------|---------|
| **pyautogui** | 基礎滑鼠鍵盤操控，跨平台 |
| **pygetwindow** | 管理視窗（最大化、切換焦點） |
| **uiautomation** | Windows 原生 UI 元素識別（推薦用於 Windows 應用程式） |

**UI 自動化的基本操作：**

| 操作 | 說明 |
|------|------|
| 找到視窗 | 依視窗標題找到目標應用程式 |
| 點擊座標 | 在螢幕特定位置點擊 |
| 輸入文字 | 模擬鍵盤輸入 |
| 截圖比對 | 找到螢幕上特定的圖示或按鈕 |
| 等待元素 | 等待特定視覺元素出現 |

> **重要提醒：** UI 自動化比 API 自動化脆弱許多——介面稍有變化（版本更新、螢幕解析度改變）就可能導致腳本失效。應加入足夠的偵錯機制，並定期維護。

#### 5. 遺留系統整合的策略

面對無法改造的舊系統，常見的整合策略：

| 策略 | 說明 | 難度 |
|------|------|------|
| **UI 自動化** | 用機器人模擬人工操作 | 低 |
| **資料庫直接存取** | 直接讀寫舊系統的資料庫 | 中（需要 IT 授權） |
| **螢幕截圖 + AI 識別** | 截取畫面，用 AI 理解並提取資訊 | 中 |
| **中介層（Middleware）** | 在舊系統外包一層 API | 高（需要開發） |

## 9/01｜第07堂｜Vibe Coding 驅動：智慧動態報表系統開發

### 學習目標

完成本堂課後，學員將能夠：

- 運用 Vibe Coding 實現從資料取得到報表生成的**端到端（End-to-End）**流程

- 建立動態資料模型，讓報表自動隨資料更新
- 輸出格式多樣的報表（Excel、HTML、PDF）

---

### 核心概念說明

#### 1. 什麼是「端到端報表系統」？

**端到端（End-to-End）**意味著整個流程從頭到尾完全自動化，不需要人工介入：

```
外部資料來源（API / 資料庫 / 檔案）
    │
    ▼ 自動擷取資料
原始資料
    │
    ▼ 資料清理與計算
處理後的數據
    │
    ▼ 套用報表模板
格式化報表
    │
    ▼ 自動輸出
Excel / PDF / HTML / 郵件附件
```

**傳統 vs. 智慧動態報表的差異：**

| | 傳統手工報表 | 智慧動態報表系統 |
|-|------------|----------------|
| 資料來源 | 手動下載、複製貼上 | 自動從 API 或資料庫取得 |
| 更新頻率 | 需要人工觸發 | 可排程定時自動執行 |
| 人力需求 | 每次都需要人力介入 | 設置一次，持續自動運行 |
| 錯誤率 | 人工操作容易出錯 | 流程一致，錯誤可追蹤 |

---

#### 2. API 的基礎概念

**API（Application Programming Interface，應用程式介面）**是讓不同軟體之間互相溝通的橋樑。

**一個生活化的比喻：**

在餐廳點餐時：
- **你** = 你的程式
- **菜單** = API 文件（說明可以點什麼、怎麼點）
- **服務生** = API
- **廚房** = 提供資料的服務

你不需要知道廚房怎麼運作，只需要按照菜單（API 文件）點餐（發送請求），服務生（API）就會把餐點（資料）送來。

**REST API 的基本結構：**

```
請求（Request）：
    方式: GET / POST / PUT / DELETE
    網址: https://api.example.com/data?param=value
    標頭: Authorization: Bearer YOUR_API_KEY
    主體: { "key": "value" }  ← POST 請求才有

回應（Response）：
    狀態碼: 200 成功 / 401 未授權 / 404 找不到 / 500 伺服器錯誤
    資料: { "result": [...] }  ← 通常是 JSON 格式
```

**常用的公開 API（適合新手練習）：**

| API 名稱 | 提供的資料 | 是否需要 Key |
|---------|-----------|------------|
| ExchangeRate-API | 匯率資料 | 是（免費） |
| OpenWeatherMap | 天氣資料 | 是（免費） |
| CoinGecko | 加密貨幣價格 | 否（部分免費） |
| REST Countries | 各國資訊 | 否 |
| 政府資料開放平台 | 台灣各類公開資料 | 否 |

---

#### 3. 動態資料建模

**靜態報表**：資料是固定的，報表也是固定的。
**動態報表**：資料隨時間變化，報表自動根據最新資料計算和呈現。

**動態報表的三個核心要素：**

1. **資料層**：從哪裡取得資料？取得頻率？
2. **計算層**：需要做哪些計算（加總、平均、同比增長）？
3. **呈現層**：如何顯示（表格、圖表、關鍵指標）？

**一個業務日報表的動態模型：**

```
計算「今日業績」：
    今日銷售 = 從資料庫取得今日所有訂單金額
    目標業績 = 從設定檔讀取本月目標 / 本月天數
    達成率 = 今日銷售 / 目標業績 * 100%
    與昨日比較 = (今日銷售 - 昨日銷售) / 昨日銷售 * 100%

呈現方式：
    KPI 卡片：今日業績 / 達成率（顏色：達成=綠色，未達成=紅色）
    長條圖：本月每日業績趨勢
    排行榜：今日業務員業績排名 Top 10
```

| 格式 | 工具 | 適合情境 |
|------|------|---------|
| **Excel (.xlsx)** | openpyxl、xlsxwriter | 給需要進一步分析資料的人 |
| **HTML** | Jinja2 + matplotlib | 在瀏覽器或郵件中直接檢視 |
| **PDF** | reportlab、weasyprint | 正式文件、合約、對外報告 |
| **PowerPoint (.pptx)** | python-pptx | 管理報告、簡報用途 |

#### 5. Vibe Coding 在複雜系統中的應用策略

當需要構建一個複雜的系統（如完整的報表生成系統），Vibe Coding 的策略是：

**「分而治之」原則：** 不要一次把整個系統描述給 AI，而是**拆解成小模組**，逐一生成和測試，再組合在一起。

```
複雜需求：「一個自動產生每日業務報表的系統」

拆解為：
  模組 1：資料取得函式（呼叫 API）
  模組 2：資料清理函式（處理缺失值、格式化）
  模組 3：指標計算函式（加總、排名、增長率）
  模組 4：報表樣式函式（設定 Excel 格式、圖表）
  模組 5：主程式（組合以上模組，設定排程）

每個模組先單獨開發和測試，最後整合。
```

### 核心概念說明

#### 1. 多通路內容行銷的挑戰

現代行銷需要同時在多個平台上發布內容：

| 平台 | 限制與特性 |
|------|-----------|
| Facebook | 長文適合，支援圖片、影片 |
| Instagram | 視覺優先，需高品質圖片，文字相對次要 |
| LinkedIn | 專業語氣，適合 B2B 內容，長文效果好 |
| X（Twitter） | 280 字元限制，短而有力 |
| LINE 官方帳號 | 台灣本地化，需要本地語氣，支援彈性選單 |
| 電子郵件電子報 | 可包含詳細資訊，需要吸引人的主旨 |

**手動管理多平台的問題：**
- 每個平台需要重新改寫適合的版本，費時費力
- 容易發布風格不一致的內容
- 人工失誤（忘記發佈、發錯版本）頻率高

---

#### 2. Prompt Engineering 用於內容生成

**Prompt Engineering（提示詞工程）**是設計和優化給 AI 的指令，讓 AI 產出更準確、更符合需求的輸出。

**控制輸出品質的關鍵 Prompt 要素：**

| 元素 | 說明 | 範例 |
|------|------|------|
| **角色設定** | 告訴 AI 它扮演什麼角色 | 「你是一位有 10 年經驗的品牌行銷專家」 |
| **目標受眾** | 描述內容的目標讀者 | 「目標受眾是 30-40 歲的台灣中階主管」 |
| **平台特性** | 說明發布平台的規則和風格 | 「這是 LinkedIn 貼文，語氣要專業，可以長一點」 |
| **內容要素** | 指定必須包含的資訊 | 「必須包含產品名稱、三個主要優點、行動號召」 |
| **格式要求** | 指定輸出的格式 | 「字數限制 200 字，要有 3 個 hashtag」 |
| **語氣規範** | 描述希望的寫作風格 | 「語氣要活潑友善，不要太制式」 |

**針對不同平台的內容改寫策略：**

```
# 輸入：一份產品資訊文件
產品名稱 = "SmartFlow AI 方案"
核心賣點 = ["節省 70% 人工時間", "無需寫程式", "3 分鐘上手"]
目標行動 = "立即申請免費試用"

# 讓 AI 改寫為各平台版本：

Facebook 版：
    語氣友善、故事化，字數 150-300 字，加入 emoji

LinkedIn 版：
    專業商務語氣，說明商業價值，字數 200-400 字，
    包含數據證明，加入 2-3 個相關 hashtag

X 版：
    濃縮核心訊息，280 字元限制，1 個強烈的 CTA

Email 主旨：
    吸引人點擊、製造好奇心，50 字元以內
```

---

#### 3. AI 指令集封裝（Function/Tool 設計）

當 Agent 執行複雜任務時，需要將整個工作流拆解為**可重複使用的工具函式**，再由 Agent 根據任務需求選擇調用哪些工具。

**內容行銷 Agent 的工具清單設計：**

```
工具 1：生成平台內容(產品資訊, 平台名稱, 語氣)
    → 輸出: 該平台的貼文草稿

工具 2：調整內容長度(文字, 目標字數)
    → 輸出: 調整後的文字

工具 3：加入 Hashtag(文字, 數量, 主題類別)
    → 輸出: 加上 hashtag 的文字

工具 4：生成圖片描述(產品資訊, 平台風格)
    → 輸出: 適合的圖片描述（可交給設計師或 AI 生圖工具）

工具 5：排程發布(平台, 內容, 發布時間)
    → 觸發對應平台 API 進行發布

工具 6：記錄發布結果(平台, 發布時間, 成功/失敗)
    → 儲存到發布記錄 Excel
```

#### 4. 平台 API 串接概念

各社群平台都提供官方 API 供開發者使用，但各自有不同的規範：

**常用平台 API 概覽：**

| 平台 | API 名稱 | 申請難度 | 主要限制 |
|------|---------|---------|---------|
| Facebook/Instagram | Meta Graph API | 中（需審核） | 每日發文次數限制 |
| LinkedIn | LinkedIn Marketing API | 中（需申請） | 需要 Page 管理員權限 |
| X（Twitter） | X API v2 | 低（基本免費） | 免費版有讀寫限制 |
| LINE 官方帳號 | LINE Messaging API | 低 | 需要在台灣申請官帳 |

**API 串接的通用流程：**

```
1. 到平台的開發者中心申請帳號
2. 建立應用程式（App），取得 API Key 和 Secret
3. 完成 OAuth 2.0 授權流程，取得 Access Token
4. 使用 Access Token 呼叫 API 發布內容
5. 處理 API 的回應（成功/失敗/限流）
```

**自動排程發布的概念：**

```
觀念：不是立即發布，而是依照最佳時間排程

研究顯示的最佳發布時間（參考）：
    Facebook: 週三 11:00, 13:00
    Instagram: 週二-週五 10:00-14:00
    LinkedIn: 週二-週四 07:00-08:00, 17:00-18:00
    X: 週一-週五 09:00, 12:00, 17:00
```

## 9/15｜第09堂｜實作：AI 智慧研報與商務情報搜集系統

### 學習目標

完成本堂課後，學員將能夠：

- 建立自動化的資料檢索與分析工作流
- 整合多個資料來源（新聞、財經網站、公開資料庫）進行情報搜集
- 使用 AI 將大量非結構化情報彙整為有商業洞察的研報
- 輸出格式化的分析文案與報告文件

---

### 核心概念說明

#### 1. 什麼是商務情報（Business Intelligence）？

**商務情報（BI）**是指透過有系統地蒐集、分析和解讀資訊，幫助企業做出更好的決策。

**情報搜集的典型應用場景：**

| 場景 | 需要搜集的資訊 | 使用目的 |
|------|--------------|---------|
| 競品分析 | 競爭對手的定價、新聞、人才動向 | 調整自身策略 |
| 市場研究 | 產業趨勢、消費者輿論、法規動向 | 投資或進入新市場的決策 |
| 供應商評估 | 廠商公司資訊、財務狀況、客戶評價 | 選擇可靠的合作夥伴 |
| 客戶洞察 | 客戶公司近期動態、新聞、財報 | 銷售前準備、個人化服務 |

**傳統情報搜集 vs. AI 自動化：**

| | 傳統方式 | AI 自動化 |
|-|--------|---------|
| 耗時 | 數小時到數天 | 數分鐘 |
| 覆蓋範圍 | 有限（人力限制） | 可掃描大量來源 |
| 品質一致性 | 因人而異 | 格式一致 |
| 即時性 | 有延遲 | 可近乎即時 |

---

#### 2. 自動化資料檢索的技術架構

**情報搜集 Agent 的資料流：**

```
任務輸入（搜集主題、關鍵字、時間範圍）
    │
    ▼ 多來源資料擷取
    ├── 新聞 API（Google News、NewsAPI）
    ├── Web 搜尋（Bing Search API、SerpAPI）
    ├── 社群媒體（Twitter/X API）
    ├── 公開資料庫（政府資料、財政部）
    └── 目標網站（Playwright 爬取）
    │
    ▼ 資料去重與篩選
過濾掉重複或不相關的資訊
    │
    ▼ AI 分析與彙整
    ├── 摘要每篇文章的重點
    ├── 識別跨文章的共同主題
    ├── 找出潛在的商業含義
    └── 排列資訊的重要性
    │
    ▼ 報告生成
結構化的研報文件（Word / PDF / HTML）
```

---

#### 3. NewsAPI 與搜尋 API

**NewsAPI** 是一個常用的新聞資料 API，提供來自全球數千個媒體的最新新聞。

**NewsAPI 的基本用法：**

```
請求參數：
    關鍵字 (q): 要搜尋的主題
    語言 (language): zh（中文）、en（英文）
    從此日期 (from): 搜尋的開始日期
    排序方式 (sortBy): publishedAt（最新）、relevancy（相關度）

回應格式：
    [
        {
            "title": "文章標題",
            "source": {"name": "媒體名稱"},
            "publishedAt": "發布時間",
            "description": "文章摘要",
            "url": "原文連結"
        },
        ...
    ]
```

**SerpAPI（搜尋引擎結果 API）：**

SerpAPI 可以以程式方式取得 Google 搜尋結果，適合需要更廣泛資料來源的情境。

---

#### 4. 研報的結構設計

一份有商業價值的研報通常包含以下結構：

```
[研報標題]
[搜集時間 / 分析範圍]

一、執行摘要（Executive Summary）
    - 3-5 條最重要的發現
    - 主要結論與建議

二、主題概覽
    - 背景說明
    - 本次分析範圍

三、資料來源分析
    - 共蒐集幾篇文章 / 幾個來源
    - 主要媒體分佈
    - 時間分佈

四、核心發現（依重要性排列）
    - 發現 1：[標題] + 分析 + 相關來源連結
    - 發現 2：...
    - 發現 3：...

五、趨勢分析
    - 近期趨勢走向
    - 潛在的機會與威脅

六、建議行動
    - 短期（1-3 個月）可採取的行動
    - 中長期策略方向

七、附錄：原始資料來源清單
```

---

#### 5. AI 分析的 Prompt 設計

研報的核心價值在於「洞察（Insight）」，而不只是「摘要（Summary）」。

**摘要 vs. 洞察的差別：**

| | 摘要 | 洞察 |
|-|------|------|
| 說明什麼 | 「這篇文章說了 A, B, C」 | 「綜合三篇報導，可以發現 XX 公司正在做 Y，這意味著市場將往 Z 方向演變」 |
| 價值 | 省去閱讀原文的時間 | 提供決策依據 |

**設計「洞察型」Prompt 的技巧：**

```
不好的 Prompt：
「請摘要以下新聞文章。」

好的 Prompt：
「以下是過去一週關於『電動車電池市場』的 10 篇新聞。
請以一位產業分析師的角度，分析：
1. 這些新聞反映出什麼重要的市場趨勢？
2. 有哪些企業的動作值得特別關注？為什麼？
3. 這對正在考慮進入這個市場的公司意味著什麼機會或風險？
請提供具體的、可行動的建議，不要只是描述事實。」
```

## 9/22｜第10堂｜實作：AI 智慧驅動視覺化簡報生成

### 學習目標

完成本堂課後，學員將能夠：

- 使用 AI 將長篇文稿或大綱自動轉化為結構化的簡報邏輯
- 使用 python-pptx 套件以程式方式生成 PowerPoint 簡報
- 自動化套用一致的設計風格至所有投影片
- 建立從「文字輸入」到「完整簡報輸出」的端到端自動化流程

---

### 核心概念說明

#### 1. 為什麼簡報製作是 AI 自動化的理想場景？

製作一份簡報通常需要：

1. 閱讀大量資料 → **AI 最擅長的摘要與結構化**
2. 決定每張投影片的內容邏輯 → **AI 的架構規劃能力**
3. 確保視覺風格一致 → **程式操控 PPT 的強項**
4. 反覆調整格式和排版 → **程式比人工快、精準**

簡報製作因此是「AI 語意能力 + 程式自動化」結合效益最大的場景之一。

---

#### 2. AI 語意架構化：從長文到投影片結構

**核心任務：** 將一份冗長的文稿或大綱，轉化為「每張投影片該說什麼」的清單。

**好的投影片結構原則：**

| 原則 | 說明 |
|------|------|
| **金字塔原則** | 結論先行，再提供支撐細節 |
| **一頁一訊息** | 每張投影片只傳達一個核心觀點 |
| **3的法則** | 能分成三點的，就分三點（容易記憶） |
| **故事弧線** | 問題 → 影響 → 解決方案 → 行動 |

**AI 架構化的 Prompt 策略：**

```
輸入：一篇 1000 字的市場分析報告

需要 AI 完成的任務：
1. 識別報告的核心論點（1-2句）
2. 拆解為 8-12 張投影片的架構
3. 每張投影片提供：
   - 投影片標題（8字以內，有力、精準）
   - 投影片類型（標題頁、大綱、內容、數據、結論）
   - 主要內容（3-5個條列重點或1段文字）
   - 建議的視覺輔助（圖表類型、圖示建議）
4. 以 JSON 格式輸出，方便程式讀取
```

---

#### 3. PowerPoint 自動化：python-pptx

**python-pptx** 是一個 Python 套件，可以用程式碼建立、修改 PowerPoint 檔案（.pptx）。

**投影片的組成元素：**

| 元素 | 說明 |
|------|------|
| **Slide（投影片）** | 每一頁投影片 |
| **Slide Layout（版面配置）** | 預設的排版模板（標題頁、內容頁等） |
| **Placeholder（接受框）** | 版面配置中的文字或圖片位置 |
| **TextFrame（文字框）** | 包含文字的容器 |
| **Paragraph（段落）** | 文字框內的一個段落 |
| **Run（文字段）** | 段落中相同格式的一段文字 |
| **Shape（形狀）** | 矩形、圓形、線條等 |
| **Chart（圖表）** | 長條圖、折線圖、圓餅圖 |

**設計一致性的實現方式：**

```
一致設計的要素：
    主題色彩：定義 3-5 個主色和輔助色
    字型規範：標題字體 / 內文字體 / 大小規格
    版面規則：每張投影片左側留白多少、標題位置固定

在 python-pptx 中：
    使用 Presentation Theme 套用整體樣式
    使用 Slide Master 統一管理母片設計
    每張投影片繼承相同的基礎設計，再加入個別內容
```

---

#### 4. 投影片類型與對應視覺設計

不同類型的投影片需要不同的版面設計：

| 投影片類型 | 適合的版面 | 主要元素 |
|-----------|-----------|---------|
| **封面頁** | 全版面視覺 + 大標題 | 主標題、副標題、日期、機構 |
| **大綱頁** | 條列式清單 | 本次簡報的章節架構 |
| **內容頁（文字）** | 標題 + 條列點 | 3-5個重點（每點一行最佳）|
| **數據頁** | 標題 + 圖表 | 一個清楚的圖表 + 簡短說明 |
| **比較頁** | 左右分欄 | 兩個選項並排比較 |
| **過渡頁** | 大字、少內容 | 章節標題，告訴觀眾接下來要講什麼 |
| **結論頁** | 重點摘要 | 3-5個最重要的帶走訊息 |
| **行動號召頁** | 醒目視覺 | 明確的下一步行動 |

### 程式碼範例（虛擬碼）

#### AI 投影片架構規劃

```
函式 規劃投影片架構(文稿內容, 簡報主題, 目標張數=10):
    提示詞 = f"""
    你是一位專業的簡報設計顧問。
    請將以下文稿設計成 {目標張數} 張左右的投影片架構。

    簡報主題：{簡報主題}
    文稿內容：
    {文稿內容}

    請以 JSON 格式回傳，結構如下：
    {{
        "title": "簡報總標題",
        "slides": [
            {{
                "index": 1,
                "type": "cover",
                "title": "...",
                "subtitle": "...",
                "points": [],
                "notes": "演講者備注"
            }},
            ...
        ]
    }}

    設計原則：
    - 第一張必須是封面（cover 類型）
    - 最後一張必須是結論或行動號召
    - 每張投影片傳達一個清楚的重點
    - 純文字的 points 每個條列不超過 20 字
    - 只回傳 JSON，不要有其他說明文字
    """

    對 重試次數 從 1 到 3:
        嘗試:
            AI回應 = 呼叫LLM(提示詞)
            結果 = 解析JSON(AI回應)
            回傳 結果
        如果發生 JSON解析錯誤:
            顯示 f"第 {重試次數} 次 JSON 解析失敗，重試中..."

    拋出例外("無法取得合法的架構 JSON")
```

#### PowerPoint 投影片生成

```
載入 pptx 套件
載入 pptx.util (Inches, Pt, Emu)
載入 pptx.dml.color (RGBColor)

常數:
    主色   = RGBColor(0x1A, 0x3A, 0x5C)  # 深藍色
    深灰色  = RGBColor(0x33, 0x33, 0x33)
    白色   = RGBColor(0xFF, 0xFF, 0xFF)
    標題字體 = "微軟正黑體"
    內文字體 = "微軟正黑體"

函式 生成投影片(架構JSON, 輸出路徑):
    簡報 = 建立新的Presentation()

    對 每張投影片資訊 在 架構JSON["slides"] 中:
        類型 = 投影片資訊["type"]
        新投影片 = 簡報.加入新投影片()

        如果 類型 == "cover":
            新投影片.背景色 = 主色
            加入文字框(新投影片, 投影片資訊["title"],
                      位置=置中, 字體=白色, 大小=40pt, 粗體=真)
            如果 有副標題:
                加入文字框(新投影片, 投影片資訊["subtitle"],
                          位置=副標題位置, 字體=白色半透明, 大小=24pt)

        否則如果 類型 == "content":
            加入標題(新投影片, 投影片資訊["title"], 顏色=主色)
            對 每個重點 在 投影片資訊["points"] 中:
                加入條列式文字(新投影片, 重點, 縮排=1)

        否則如果 類型 == "transition":
            新投影片.背景色 = 主色
            加入置中大字(新投影片, 投影片資訊["title"], 顏色=白色, 大小=36pt)

        # 加入頁碼（封面除外）
        如果 類型 != "cover":
            加入頁碼(新投影片, 投影片資訊["index"])

    簡報.儲存(輸出路徑)
    顯示 f"簡報已儲存：{輸出路徑}"
```

---

### 核心概念說明

#### 1. 客服自動化的商業價值

**數字說話：**
- 企業客服部門平均每天處理數百到數千封郵件
- 重複性問題（FAQ）通常佔來信量的 60-70%
- 人工閱讀並回覆每封郵件平均需要 5-15 分鐘

**AI 可以解決的痛點：**

| 痛點 | AI 解決方案 |
|------|------------|
| 來信量大、人力不足 | 自動分類 + 草稿生成，大幅縮短每封的處理時間 |
| 緊急信件淹沒在一般信件中 | AI 自動識別優先級，確保緊急案件不被遺漏 |
| 回覆品質因人而異 | AI 提供標準化草稿，確保品質一致 |
| 夜間或假日無法即時回覆 | 24小時自動發送初步響應，告知客戶已收到並將跟進 |

---

#### 2. 郵件分類的維度設計

一個有效的客服郵件分類系統需要多個維度同時分析：

**維度 1：意圖分類（Intent Classification）**

| 意圖類型 | 說明 | 建議處理時限 |
|---------|------|------------|
| 產品詢問 | 詢問功能、規格、價格 | 24小時 |
| 訂單狀態 | 查詢訂單進度 | 4小時 |
| 退換貨申請 | 要求退款或換貨 | 2小時 |
| 投訴/抱怨 | 對產品或服務不滿 | 1小時 |
| 緊急問題 | 系統故障、安全問題 | 立即 |
| 讚美/感謝 | 正面回饋 | 48小時 |
| 垃圾郵件 | 廣告或無關信件 | 忽略 |

**維度 2：情感分析（Sentiment Analysis）**

| 情感程度 | 判斷依據 | 影響策略 |
|---------|---------|---------|
| 強烈負面 | 語氣激烈、出現威脅或法律字眼 | 立即升級，主管介入 |
| 輕微負面 | 不滿但語氣平和 | 優先處理，同理心回覆 |
| 中性 | 無明顯情緒 | 標準處理 |
| 正面 | 感謝、讚美 | 標準回覆，可回覆感謝 |

**維度 3：複雜程度**

| 複雜程度 | 說明 | 處理方式 |
|---------|------|---------|
| 可自動化 | 標準問題，有固定答案 | AI 直接生成回覆草稿 |
| 需人工判斷 | 個案處理，需查詢資料系統 | AI 提供資訊，人工決策 |
| 需升級 | 超出一般客服權限 | 轉交主管或專責部門 |

---

#### 3. 異議處理的決策樹設計

**異議處理（Complaint Handling）**是客服中最具挑戰性的場景，需要：
1. 準確理解客戶的不滿點
2. 表達同理心
3. 提供可接受的解決方案
4. 確保客戶感到被重視

**異議處理的決策流程：**

```
收到投訴郵件
    │
    ▼ AI 分析：問題類型是什麼？
    ├── 產品品質問題
    │       │
    │       ├── 在保固期內？是 → 提供免費維修/換貨選項
    │       └── 超過保固期？是 → 提供付費維修選項，視情況提供折扣
    │
    ├── 服務態度問題
    │       │
    │       └── 升級主管，致歉並調查內部流程
    │
    ├── 物流延誤問題
    │       │
    │       ├── 公司責任？是 → 致歉 + 追蹤 + 補償方案
    │       └── 物流公司責任？是 → 告知原因 + 協助追蹤
    │
    └── 未達廣告宣稱的問題
            │
            └── 法務確認後再回覆，避免直接承認
```

#### 5. 資料安全與個資保護

客服郵件通常包含大量個人資料，在使用 AI 處理時需特別注意：

**重要原則：**

| 原則 | 說明 |
|------|------|

| **記錄存取** | 記錄哪些郵件被 AI 處理，保留稽核軌跡 |
| **員工教育** | 確保所有使用人員了解個資保護規範 |
| **使用條款確認** | 確認 LLM 服務商的資料使用政策是否符合公司合規要求 |

4. 生成每封郵件的「摘要卡」（包含分類結果和關鍵資訊）
5. 對可自動化的郵件，生成回覆草稿並存入草稿箱
6. 對需升級的郵件，發送內部通知給主管（使用 LINE Notify 或郵件）
7. 將所有處理結果記錄到 Excel（含：處理時間、分類結果、是否有草稿）
8. 生成每日客服情況統計報表
```

### 核心概念說明

#### 1. 多 Agent 協作系統

**單一 Agent vs. 多 Agent 系統**

| | 單一 Agent | 多 Agent 系統 |
|-|-----------|------------|
| 適合場景 | 單一明確的線性任務 | 複雜、多面向的任務 |
| 優點 | 設計簡單、好維護 | 可平行處理、分工明確 |
| 缺點 | 複雜任務時上下文過長 | 協調邏輯較複雜 |

**多 Agent 協作的典型架構：**

```
       ┌────────────────────────────────────┐
       │          協調者 Agent               │
       │      (Orchestrator Agent)           │
       │  接收任務，拆解並分配給子 Agent      │
       └──────┬───────────┬─────────────────┘
              │           │
    ┌─────────▼──────┐  ┌─▼──────────────┐
    │  資料搜集 Agent │  │  資料分析 Agent │
    │                │  │                │
    │ 搜集各地區新聞  │  │ 分析趨勢與模式 │
    └─────────┬──────┘  └─┬──────────────┘
              │            │
              └─────┬──────┘
                    ▼
          ┌─────────────────┐
          │   報告生成 Agent  │
          │  整合結果，輸出   │
          └─────────────────┘
```

#### 2. 全球新聞情報系統的需求分析

**系統目標：**

每天自動收集全球主要媒體的新聞，依主題分類後，提供趨勢分析和異常訊號偵測。

**系統需要解決的挑戰：**

| 挑戰 | 說明 | 解決方案 |
|------|------|---------|
| 多語言 | 英文、中文、日文等不同語言 | 使用多語言 LLM 或翻譯 API |
| 資料量大 | 每天可能有數百篇新聞 | 分批處理 + 重要性過濾 |
| 去重複 | 同一事件被多家媒體報導 | 語意相似度過濾 |
| 趨勢識別 | 找出突然增加的話題 | 關鍵字頻率時序分析 |
| 來源可信度 | 不同媒體的可信程度不同 | 建立媒體可信度白名單 |

#### 3. 跨語系資料整合

**多語言處理的兩種策略：**

**策略 A：翻譯後統一處理**
```

```

優點：保留語意精確度、省去翻譯步驟
缺點：需要 LLM 支援多語言能力（GPT-4o、Claude 均支援）
```

**本課程採用策略 B（更簡單且效果好）：**

#### 4. 趨勢分析的基本方法

**什麼是「趨勢」？**

趨勢分析的目的是回答：「關於某個主題，最近的討論是增加還是減少？有沒有突然的爆發？」

**簡單的趨勢分析方法：**

| 方法 | 說明 | 適用情境 |
|------|------|---------|
| **關鍵字頻率統計** | 計算特定關鍵字在不同時間段出現的次數 | 追蹤熱門話題的消長 |
| **新聞數量時序圖** | 以折線圖呈現每日/每週的報導數量 | 識別討論高峰 |
| **情感趨勢** | 追蹤特定主題的情感從正面變負面或反之 | 品牌聲譽監控 |
| **異常偵測** | 找出短時間內大幅増加的主題 | 快速識別突發事件 |

**趨勢視覺化的常用圖表：**

| 圖表類型 | 適合展示 |
|---------|---------|
| 折線圖 | 隨時間的數量變化 |
| 熱力圖 | 主題 × 時間的強度分佈 |
| 詞雲 | 高頻關鍵字的視覺化 |
| 長條圖 | 各主題的報導量比較 |

## 10/13｜第13堂｜案例分析：企業供應鏈數據管理與結構化工程

### 學習目標

完成本堂課後，學員將能夠：

- 分析企業供應鏈數據管理的實際痛點與自動化機會
- 從格式不一的廠商報價單中自動提取關鍵資訊
- 建立自動化的報價單歸檔與版本管理系統
- 實作 KPI 指標的自動化計算與多廠商比對功能

---

### 核心概念說明

#### 1. 企業供應鏈數據管理的痛點

**典型企業場景：**

一家製造業公司，每次採購物料時需要：
1. 向 10-20 家廠商詢價
2. 各廠商用自己的格式回傳報價單（Excel、PDF、Word 都有）
3. 採購人員逐一打開報價單，手動複製關鍵資料到比較表
4. 計算各廠商的綜合評分（價格、交期、品質等）
5. 製作比較報告提交主管審核

**這個流程的問題：**

| 問題 | 影響 |
|------|------|
| 格式不統一 | 每份報價單都要重新閱讀理解結構 |
| 手動複製資料 | 容易出現輸入錯誤 |
| 比較邏輯複雜 | 要同時考慮多個維度，容易遺漏 |
| 歸檔不系統 | 找歷史報價困難，版本管理混亂 |
| 耗時 | 採購人員的大量時間花在這些低附加價值的工作 |

---

#### 2. 異質資料提取的挑戰

**為什麼廠商的報價單格式不統一？**

- 各廠商有自己的 ERP 系統，匯出格式各異
- 有些廠商習慣用 Excel 模板，表格結構不同
- 有些廠商只用 PDF，甚至是掃描紙本
- 欄位名稱不一樣（「單價」vs「每件価格」vs「Unit Price」）
- 計算邏輯不同（含稅/不含稅、是否包含運費）

**AI 在異質資料提取的優勢：**

傳統的程式處理異質資料需要為每種格式寫獨立的解析邏輯（維護成本極高），而 LLM 能夠**理解各種格式的語意**，直接提取結果。

---

#### 3. KPI 指標設計

比較廠商時，通常不能只看價格，需要考慮多個維度：

**採購 KPI 評估框架（範例）：**

| KPI 指標 | 說明 | 權重（可自訂） |
|---------|------|--------------|
| 單價 | 每件/每批的價格 | 40% |
| 交期 | 從下單到交貨的天數 | 25% |
| MOQ | 最低訂購量（影響彈性） | 10% |
| 付款條件 | 幾天內付款，是否有折扣 | 10% |
| 品質等級 | ISO 認證、過去的不良率 | 15% |

**KPI 加權評分計算：**

```
廠商總分 = 
    (單價分數 × 40%) +
    (交期分數 × 25%) +
    (MOQ分數 × 10%) +
    (付款條件分數 × 10%) +
    (品質等級分數 × 15%)

各指標的分數計算：
    單價分數 = 100 × (最低單價 / 該廠商單價)
    交期分數 = 100 × (最短交期 / 該廠商交期)
    ...
```

---

#### 4. 報價單歸檔系統設計

一個好的報價單歸檔系統需要：

**資料夾結構設計：**

```
/供應商報價管理/
    /[廠商名稱]/
        /[詢價品項]/
            /[年份]/
                原始報價單_2025Q3_V1.pdf
                原始報價單_2025Q3_V2.xlsx  ← 廠商修改後的版本
                解析結果_2025Q3.json        ← AI 提取的結構化資料
                比較報表_2025Q3.xlsx        ← 最終的比較結果
```

**版本管理的重要性：**

廠商有時會在報價後調整價格，版本管理讓你能：
- 追蹤哪個版本的報價最終被採用
- 記錄廠商的報價歷史，用於下次議價的依據
- 稽核時提供完整的報價紀錄

---

#### 5. 供應鏈場景的特殊考量

在供應鏈場景中，AI 自動化需要特別注意：

**資料準確性要求極高：**

| 風險 | 說明 | 控制措施 |
|------|------|---------|
| AI 提取錯誤 | 金額、數量提取有誤 | 所有提取結果需人工確認 |
| 匯率換算 | 外幣報價需要正確換算 | 匯率來源要可追溯 |
| 幣別混淆 | 同一份報價單可能混用幣別 | 明確標記每個金額的幣別 |
| 單位不統一 | kg vs g、pcs vs 箱 | 統一換算為標準單位 |

```
載入 pdfplumber, pandas, docx, openai, json 套件

函式 讀取檔案內容(檔案路徑):

函式 提取報價資料(檔案路徑):

    原始內容 = 讀取檔案內容(檔案路徑)

    {原始內容}

    請提取所有的報價資訊，以 JSON 格式回傳。

    特別注意：
    - 若資訊不明確，填入 "UNKNOWN" 並將 AI信心度 設為「低」

#### KPI 評分計算

```
函式 計算KPI評分(廠商報價清單, KPI權重設定):
    評分結果 = []

    # 計算各指標的最佳值（用來算相對分數）
    最低單價 = 找最小值([廠商["品項"][0]["單價"] for 廠商 in 廠商報價清單])
    最短交期 = 找最小值([轉換為天數(廠商["交期"]) for 廠商 in 廠商報價清單])

    對 每個廠商 在 廠商報價清單 中:
        各項分數 = {}

        # 單價分數（越低越好）
        廠商單價 = 廠商["品項"][0]["單價"]
        各項分數["單價"] = (最低單價 / 廠商單價) * 100

        # 交期分數（越短越好）
        廠商交期 = 轉換為天數(廠商["交期"])
        各項分數["交期"] = (最短交期 / 廠商交期) * 100

        # 加權計算總分
        總分 = 0
        對 每個KPI, 分數 在 各項分數.items():
            權重 = KPI權重設定.get(KPI, 0)
            總分 += 分數 * 權重 / 100

        評分結果.加入({
            "廠商名稱": 廠商["廠商資訊"]["廠商名稱"],
            "各項分數": 各項分數,
            "加權總分": round(總分, 2),
            "推薦": 總分 >= 80  # 80分以上標記為推薦
        })

    # 依總分排序
    回傳 排序(評分結果, 依照="加權總分", 降序=真)
```

## 10/20｜第14堂｜案例分析：敏捷管理自動化—智慧週報生成系統

### 學習目標

完成本堂課後，學員將能夠：

- 了解敏捷（Agile）專案管理的基本概念與資料結構
- 整合來自多個來源的跨專案工作資料
- 使用 AI 從原始工作紀錄中自動提取關鍵里程碑
- 將原始工作資料轉化為具備管理深度的 PPT 決策報表

---

### 核心概念說明

#### 1. 敏捷管理的週報痛點

**典型情境：**

PM（專案經理）每週五要整理週報，流程通常是：

1. 從 Jira 匯出本週的任務清單（CSV）
2. 打開 Excel 手動計算完成率、延遲任務數、風險項目
3. 詢問各組組長本週的主要成果
4. 整理以上資訊，寫成 Word 報告或 PowerPoint
5. 每週重複這個 2-3 小時的工作

**企業的實際痛點：**

| 問題 | 影響 |
|------|------|
| 資料散落各處 | 需要從多個系統蒐集，費時且易遺漏 |
| 格式不一致 | 不同組別的周報格式不同，彙整困難 |
| 分析深度不足 | 時間緊迫下，大多是數字羅列，缺乏洞察 |
| 版本管理問題 | 找上週的報告耗時 |
| 高重複性工作 | PM 寶貴的時間被這類工作佔據 |

---

#### 2. 敏捷管理的核心資料結構

要自動化週報生成，需要理解敏捷管理的基本資料：

**Sprint（衝刺）：**
- 敏捷開發的基本工作週期，通常 1-2 週
- 每個 Sprint 有明確的開始和結束日期
- Sprint 結束後要達成一個「可交付的成果」

**Story / Task：**
- Sprint 中的工作任務
- 每個任務有：標題、負責人、狀態、預估工時、實際工時、優先級

**里程碑（Milestone）：**
- 專案的重要轉折點或交付節點
- 不是每週都有，但需要在報告中特別標注

**KPI 指標：**

| 指標 | 計算方式 | 說明 |
|------|---------|------|
| Sprint 完成率 | 完成任務數 / 計劃任務數 | 衡量計畫執行能力 |
| 工時燃盡率 | 已用工時 / 計畫工時 | 判斷是否超支 |
| Bug 密度 | 發現的 Bug 數 / 完成的功能數 | 衡量品質 |
| 阻塞任務比例 | 阻塞中任務數 / 總任務數 | 識別風險 |

---

#### 3. 跨專案資料整合架構

當公司有多個並行專案時，週報需要呈現所有專案的整合視圖：

**資料來源可能包含：**

```
資料來源 1：Jira / Trello / Asana
    └── 任務清單（CSV 或 API）

資料來源 2：Git（GitHub / GitLab）
    └── Commit 記錄（代碼提交歷史）

資料來源 3：日常工作紀錄
    └── 會議記錄（Word / Notion）
    └── 組員的週記（純文字）

資料來源 4：時程表
    └── 原始計畫甘特圖（Excel）
```

**整合挑戰：**

- 不同系統的任務 ID 不相同
- 同一個任務在不同系統中可能有不同的名稱
- 時區不一致
- 部分系統可能暫時無法連接

#### 4. AI 提取里程碑的邏輯

原始工作紀錄通常是這樣的文字：

> 「本週完成了登入模組的單元測試，所有 32 個測試案例通過。前端 UI 設計稿已獲客戶確認，可以開始實作。API 文件初版完成，已送審。」

AI 需要從這段文字中識別：
- **里程碑事件**：「所有 32 個測試案例通過」→ 測試完成里程碑
- **待追蹤事項**：「已送審」→ 有待確認的項目
- **相依關係**：「已獲客戶確認，可以開始實作」→ 解鎖了下一個任務

**AI 識別里程碑的 Prompt 設計：**

```
你是一位資深的 PM，請從以下工作紀錄中識別本週的關鍵里程碑。
里程碑的定義：
1. 重要功能完成並通過驗收
2. 關鍵決策已獲批准
3. 重要的外部依賴已解決
4. 階段性交付物完成

對於每個里程碑，請說明：
- 里程碑名稱（簡潔的標題）
- 達成日期
- 影響（對專案的意義）
- 下一步行動

工作紀錄：[內容]
```

#### 5. PPT 決策報表設計原則

面向管理層的 PPT 報告，與面向執行層的工作報告截然不同：

**管理層關注的問題：**
- 我們本週有沒有達成目標？
- 哪裡有風險需要我關注？
- 有沒有需要我做決定的事項？

**PPT 簡報頁面規劃：**

| 頁碼 | 頁面標題 | 內容 |
|-----|---------|------|
| 1 | 封面 | 週報標題、週次、報告日期 |
| 2 | 本週整體健康度 | 交通燈狀態（紅/黃/綠）+ 一句話摘要 |
| 3 | 關鍵里程碑 | 本週達成 + 下週預計 |
| 4 | 各專案 KPI 儀表板 | 完成率、工時燃盡、品質指標的視覺化 |
| 5 | 風險與阻塞項目 | 需要管理層關注的問題清單 |
| 6 | 需要決策的事項 | 具體的決策請求，附上選項與建議 |
| 7 | 下週計畫 | 各專案下週的主要目標 |

函式 提取里程碑(任務清單, 工作紀錄文字):

        "達成日期": "YYYY-MM-DD",

        "影響": "對整體專案進度的影響",
        "後續行動": "這個里程碑解鎖了什麼下一步"

    LLM回應 = 呼叫LLM(提示詞, 格式=JSON模式)

    你是一位高階 PM，需要向 CXO 報告本週專案狀況。
    
    KPI 數據：
    {KPI數據}
    
    關鍵里程碑：
    {里程碑清單}
    
    風險事項：
    {風險清單}
    
    請生成一段 3-5 句的執行摘要，使用管理層的語言：
    - 不要用技術術語
    - 強調業務影響而非技術細節

    """

    回傳 摘要

#### PPT 生成

```
載入 python_pptx 套件

函式 生成週報PPT(分析結果, 模板路徑, 輸出路徑):
    簡報 = 開啟簡報(模板路徑)

    # 封面頁（模板第 0 頁）
    封面頁 = 簡報.slides[0]
    設定文字框(封面頁, "標題佔位符", f"專案週報 W{分析結果['週次']}")
    設定文字框(封面頁, "日期佔位符", 分析結果["日期範圍"])

    # 整體健康度頁（模板第 1 頁）
    健康度頁 = 簡報.slides[1]
    顏色 = 判斷健康度顏色(分析結果["KPI"])
    設定圓形顏色(健康度頁, 顏色)
    設定文字框(健康度頁, "摘要佔位符", 分析結果["管理層摘要"])

    # KPI 儀表板頁（模板第 2 頁）
    KPI頁 = 簡報.slides[2]
    對 每個專案 在 分析結果["各專案KPI"] 中:
        顏色 = "紅色" 如果 專案["完成率"] < 70 否則 "綠色"
        新增條狀圖(KPI頁, 專案名稱=專案["名稱"], 完成率=專案["完成率"], 顏色=顏色)

    # 里程碑頁（模板第 3 頁）
    里程碑頁 = 簡報.slides[3]
    里程碑表格資料 = [
        ["里程碑", "達成日期", "重要性"],
        *[[m["名稱"], m["達成日期"], m["描述"]] for m in 分析結果["里程碑"]]
    ]
    新增表格(里程碑頁, 里程碑表格資料)

    # 風險與決策頁（模板第 4 頁）
    風險頁 = 簡報.slides[4]
    對 i, 風險 在 enumerate(分析結果["風險清單"]):
        新增條列(風險頁, i, f"⚠ {風險}")
    對 i, 決策 在 enumerate(分析結果["決策事項"]):
        新增條列(風險頁, i + 10, f"🎯 {決策['問題']}\n   建議：{決策['建議']}")

    簡報.save(輸出路徑)
    顯示("✅ 週報已生成：" + 輸出路徑)
    回傳 輸出路徑

函式 判斷健康度顏色(KPI):
    完成率 = KPI["sprint完成率"]
    阻塞率 = KPI["阻塞率"]

    如果 完成率 >= 80 且 阻塞率 <= 10:
        回傳 "綠色"
    否則如果 完成率 >= 60 且 阻塞率 <= 20:
        回傳 "黃色"
    否則:
        回傳 "紅色"
```
